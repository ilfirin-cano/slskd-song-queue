# slskd Song Queue

Отдельный HTTP-сервис с веб-интерфейсом: принимает список композиций, ищет совпадения через API уже запущенного контейнера slskd и добавляет выбранные файлы в его очередь загрузок. Сам slskd в этот Docker Compose не входит и не устанавливается повторно.

## Подключение к существующему slskd

1. Убедитесь, что контейнер slskd запущен:

   ~~~bash
   docker ps
   ~~~

2. Узнайте Docker-сеть, к которой подключён контейнер (здесь предполагается, что его имя — slskd):

   ~~~bash
   docker inspect slskd --format '{{range $name, $_ := .NetworkSettings.Networks}}{{println $name}}{{end}}'
   ~~~

   Используйте имя одной из этих сетей в переменной SLSKD_NETWORK. Если контейнер называется иначе, укажите его DNS-имя или сетевой alias в SLSKD_URL.

3. Создайте локальный файл настроек:

   ~~~bash
   cp .env.example .env
   ~~~

4. Отредактируйте .env:
   - SLSKD_NETWORK — существующая Docker-сеть slskd, например slskd_default;
   - SLSKD_URL — адрес API slskd внутри этой сети, обычно http://slskd:5030;
   - SLSKD_API_KEY — API key из настроек Web/API slskd.

5. Запустите только приложение:

   ~~~bash
   docker compose up -d --build
   ~~~

6. Откройте веб-интерфейс: http://localhost:8080.

Важно: внешний Docker network должен уже существовать. Compose этого проекта не создаёт, не перезапускает и не изменяет контейнер slskd.

## Выбор и поиск аудио

- В очередь добавляются только файлы с расширениями .mp3 и .flac. Файлы .lrc, обложки и остальные форматы игнорируются.
- При выборе из результатов MP3 имеет приоритет над FLAC. Внутри каждого формата выше ранжируются более точные совпадения.
- В блоке «Настройки поиска» в веб-интерфейсе можно задать длительность первичного поиска (5–180 секунд), длительность повторного поиска (10–300 секунд) и включить/выключить второй проход.
- По умолчанию первичный поиск длится 25 секунд. Ненайденные треки автоматически проходят второй, более тщательный поиск длительностью 60 секунд. Для него используется дополнительный поисковый запрос только по названию, удаляются некоторые уточняющие суффиксы вроде feat., а лимит результатов увеличен.
- Повторный проход начинается после первичной обработки всего списка, не дожидаясь окончания уже запущенных загрузок. Поэтому slskd продолжает скачивать поставленные файлы, пока приложение ищет следующие треки.
- Поисковые операции самого API выполняются последовательно из-за ограничения slskd 0.24+ на одновременные запросы. Запросы добавления в очередь также сериализованы; передача уже поставленных файлов идёт независимо.

## Использование

Вставьте по одной композиции на строку в формате Исполнитель — Название, Исполнитель - Название или Artist / Title. Нажмите «Найти и скачать». Состояния и прогресс обновляются автоматически примерно раз в 1,5 секунды.

Можно отправлять список через API:

~~~bash
curl -X POST http://localhost:8080/songs \
  -H 'Content-Type: application/json' \
  -d '{"songs":[{"artist":"Daft Punk","title":"Giorgio by Moroder"},{"artist":"Massive Attack","title":"Teardrop"}]}'
~~~

Основные endpoints:
- GET /health — состояние сервиса.
- GET /settings — значения настроек поиска по умолчанию.
- POST /songs — создать batch поиска.
- GET /batches/{batch_id} — получить статусы и прогресс треков.

## Настройки окружения

| Переменная | Назначение | По умолчанию |
|---|---|---:|
| SEARCH_DURATION_SECONDS | Длительность первичного поиска | 25 |
| SEARCH_WAIT_GRACE_SECONDS | Дополнительное ожидание ответа после поискового таймаута slskd | 5 |
| DEEP_SEARCH_DURATION_SECONDS | Длительность одного запроса второго прохода | 60 |
| DEEP_SEARCH_MIN_MATCH_SCORE | Порог совпадения второго прохода | 0.50 |
| DEEP_SEARCH_RESPONSE_LIMIT | Максимум пользователей с результатами во втором проходе | 250 |
| RETRY_NOT_FOUND_BY_DEFAULT | Включать повторный поиск по умолчанию | true |
| MIN_MATCH_SCORE | Порог совпадения первого прохода | 0.52 |
| SLSKD_429_RETRIES | Число повторов при HTTP 429 | 5 |

Эти значения можно переопределять в .env. Длительность и включение повторного прохода для конкретного списка можно менять непосредственно в веб-интерфейсе.

## Обработка HTTP 429 от slskd

Новые версии slskd ограничивают число одновременных поисковых и enqueue-операций. Приложение сериализует такие API-запросы между всеми batch, а при ответе HTTP 429 повторяет запрос с экспоненциальной задержкой. Уже поставленные в очередь загрузки продолжают передаваться параллельно с последующими поисками.

## Важные замечания

- Сервис подключается к существующему slskd по внутренней Docker-сети; он не содержит отдельного экземпляра slskd.
- Состояние batch хранится в памяти процесса. После перезапуска song-queue история batch не восстанавливается, но сами трансферы продолжают управляться slskd.
- Реализация ориентирована на API slskd; названия полей и формы ответов могут зависеть от версии. При несовпадении проверьте API вашей сборки slskd.
- Не публикуйте порты приложения и slskd в интернет без аутентификации и сетевой защиты. Не добавляйте .env или API key в Git.
- Соблюдайте законодательство об авторском праве и правила Soulseek.
